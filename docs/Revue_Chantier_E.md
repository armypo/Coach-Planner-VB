# Revue adversariale du chantier E — trouvailles confirmées

> Revue indépendante du 2026-09-01 (5 lentilles × réfutation adversariale, 64 agents) sur le diff `b391a49..e4c919d` (E1→E4). **54 trouvailles confirmées** (3 CRITIQUES, 20 HAUTES), 5 réfutées. Les 310/310 tests passent mais sont des tests PURS (mappings, imports in-memory) — aucun n'exerce les ACL CloudKit réelles, la concurrence multi-appareils ni les échecs réseau : c'est pourquoi la livraison semblait saine.
>
> **Ce document est la SPEC du correctif E'** — le chantier E est GELÉ (kill-switch ou revert partiel, décision fondateur en cours) tant que les CRITIQUES et HAUTES ne sont pas résolues.

## Synthèse des familles de problèmes

1. **ACL Public DB vs écriture multi-coachs (LE problème architectural)** : la Public DB n'autorise l'écriture d'un record existant qu'à son CRÉATEUR. E4 fait écrire tous les coachs sur les MÊMES recordNames → soit les sweeps des assistants échouent en permanence (ACL par défaut/durcies), soit on ouvre l'écriture au monde (tampering). Piste de refonte : records PAR ÉCRIVAIN (recordName suffixé par l'ID de l'écrivain, merge à l'import) ou sortie de la Public DB (CKShare = migration Core Data).
2. **Aucune propagation de suppression** : tout ce qui est supprimé localement (match, exercice, item de bibliothèque, formation) RESSUSCITE à l'import suivant — et regonfle les cumuls carrière pour les StatsMatch. Il faut des tombstones ou la dé-publication systématique dans les cascades.
3. **Écho de republication + fenêtres du seuil** : import-puis-publication re-pousse ce qu'on vient d'importer ; `derniereSyncDate` globale (pas par équipe), posée en FIN de sweep, avancée même quand le mode match SAUTE les points → pertes définitives.
4. **Binaires (dessins)** : un échec de lecture CKAsset écrase le dessin LOCAL à nil, puis l'écho propage la destruction au miroir ; seuil CKAsset par champ (record > 1 Mo possible) ; re-téléchargement intégral à chaque foreground.
5. **PII de mineurs world-readable** : statut de santé (blessé/malade) + attestation parentale nominative publiés en clair (E1) ; notes libres du scouting/bibliothèque ; spoofing possible (l'import ne vérifie jamais le créateur du record — poison LWW par date future).
6. **Mode match troué** : un coach NON-preneur qui ouvre/ferme le live purge les points des autres en Public DB (CRITIQUE) ; l'import n'est pas suspendu pendant le live ; `modeMatchActif` non persistant.

## Trouvailles (triées par sévérité)

### 1. [CRITIQUE] E4 bidirectionnel incompatible avec les ACL de la Public DB — soit tampering mondial, soit sweeps en échec permanent

- **Lentille** : securite-pii · **Fichiers** : `Playco/Services/CloudKitSharingService.swift:70 (planSync) + Playco/Services/CloudKitSharingService+Publication.swift:215 (recordPublicAJour)`
- **Description** : Par défaut, la Public DB CloudKit n'autorise l'écriture d'un record existant qu'à son CRÉATEUR (World=read, Authenticated=create, Creator=write). E4 fait pourtant écrire TOUS les coachs sur les MÊMES recordNames déterministes (« exercice-<uuid> », « joueur-<uuid> », « stats-<uuid> ») via fetch-puis-modifier : l'assistant qui modifie un record créé par le head coach verra son save rejeté (permission failure). Pire, le sweep republie aussi les items qu'il vient d'importer (leur dateModification > seuil et l'anti-boucle « égalité = no-op » ne s'applique qu'à l'IMPORT, pas à la publication) : tout appareil qui importe un record d'un autre coach tente ensuite de le réécrire, échoue, throw → le sweep entier avorte, derniereSyncDate n'avance plus, erreur à chaque cycle. Inversement, si les Security Roles sont ouverts (Authenticated=write) pour faire fonctionner E4, alors n'importe quel utilisateur iCloud muni de l'app peut modifier/supprimer les records de n'importe quelle équipe — le durcissement Dashboard « write créateur-seul » documenté comme prérequis prod (piège #26/#27, docs/Securite_AbonnementPublicDB.md) casse E4. Les 310 tests sont tous purs (mappings, imports in-memory) et n'exercent jamais les ACL réelles ; la contradiction n'est détectable qu'à deux appareils/deux Apple ID.
- **Scénario** : Coach A crée l'exercice X et le publie (record créé sous l'Apple ID de A). L'assistant B importe X, l'édite (bump dateModification), puis son sweep appelle publierExercice → recordPublicAJour récupère le record de A, save → permission failure du serveur → throw → le sweep de B s'arrête là à CHAQUE cycle (stratégies/scouting/stats jamais publiés ensuite, seuil gelé, self.erreur affiché). L'édition de B n'atteint jamais A : la parité E4 est inopérante. Variante sans aucune édition : B importe les StatsMatch publiés par A après le match du soir (dateModification > seuil de B) → le sweep de B les republie → même échec → sync coincée.
- **Vérification (preuves)** : TROUVAILLE CONFIRMÉE [CRITIQUE]. (1) RecordNames déterministes partagés entre tous les écrivains : publierSeance/publierJoueur/publierExercice etc. (+Publication.swift:307,313,364) via recordPublicAJour (l.215), et planSync (CloudKitSharingService.swift:70-77) fait publier tous les rôles coach. (2) Le sweep republie bien les items importés : l'import pose dateModification locale = remote (+Import.swift:312,392), ContentView.swift:151-166 importe PUIS publie, seuil = derniereSyncDate capturé en +Publication.swift:130 ; la baseline Date() n'est posée qu'après l'import INITIAL (+Import.swift:130), pas dans syncDepuisPublic — tout item modifié par un autre coach depuis le dernier cycle est donc re-poussé vers le record d'autrui ; l'anti-boucle « égalité = no-op » ne couvre que l'import. (3) Un seul do/catch dans publierMisesAJourCoach (+Publication.swift:132-205) : le premier throw avorte le sweep, saute derniereSyncDate = Date() (l.201) et pose self.erreur — aucune gestion de CKError.permissionFailure dans tout le service. (4) La contradiction est actée par le dépôt lui-même : docs/Journal_Pivot_CoachFirst.md:85 exige en pré-prod « rôle d'écriture créateur-seul sur les nouveaux types » (posture de docs/Securite_AbonnementPublicDB.md §3), incompatible avec l'écriture multi-coachs d'E4 sur les mêmes recordIDs ; et sous les ACL CloudKit PAR DÉFAUT (_creator write seul sur record existant), la panne existe déjà aujourd'hui. (5) Aucun test n'exerce les ACL réelles (mappings purs/in-memory). Scénario minimal : coach A édite une séance à T1 ; l'assistant B (autre Apple ID) synchronise à T2 sous creator-write → import applique T1 > seuil → publierSeance sur le record créé par A → permissionFailure → catch l.202 → sweep arrêté à chaque cycle, seuil gelé, les éditions de B n'atteignent jamais A. Alternative (ouvrir _icloud write pour faire marcher E4) = n'importe quel utilisateur iCloud connaissant un codeEquipe peut écraser les records de l'équipe — violation du piège #26.

### 3. [CRITIQUE] Purge des fantômes : un coach non-preneur de stats qui ouvre puis ferme le Mode live supprime de la Public DB les points qu'il n'a pas localement

- **Lentille** : d6-mode-match · **Fichiers** : `Playco/Services/CloudKitSharingService+Analyse.swift:150-161 (+ Playco/Views/Matchs/MatchLiveSplitView.swift:123-137, Playco/Views/Seances/MatchDetailView.swift:160-168)`

- **Scénario** : Le coach A prend les stats d'un match et le finalise : ~150 PointMatchPartage publiés. L'assistant B (D6, mêmes droits) n'a pas encore importé ces points (premier lancement, hors-ligne, ou bug de borne incrémentale — trouvaille suivante). - **Vérification (preuves)** : La trouvaille TIENT — chaque maillon du scénario est vérifié dans le code réel :

1. 2. `publierAnalyseMatch` (Analyse.swift:303-318) passe toujours `supprimerFantomes: true` et fetch les points depuis le contexte local de l'appelant, sans vérifier ni `statsEntrees` ni que l'appelant possède des points.

Scénario minimal : coach A finalise un match (~150 PointMatchPartage publiés, `derniereSyncDate` de A avancée). Assistant B, en ligne, dont l'import des points n'est pas terminé (ou pas commencé), ouvre « Mode en direct » sur ce match et le referme → `onDisappear` → purge → tous les points de A supprimés de la Public DB, jamais republiés. ### 4. [HAUTE] Import fondé sur les champs du record (codeEquipe, *ID, dateModification), jamais sur le créateur — injection et écrasement LWW par un tiers

- **Lentille** : securite-pii · **Fichiers** : `Playco/Services/CloudKitSharingService+Preparation.swift:129,287 + Playco/Services/CloudKitSharingService+Analyse.swift:65 + Playco/Services/CloudKitSharingService+Import.swift:294`
- **Description** : importerExercice/importerStrategie/importerScouting/importerBibliotheque/importerStatsMatch/importerJoueur retrouvent l'entité locale par le CHAMP *ID du record et appliquent un LWW strict par dateModification, sans aucune vérification de l'identité du créateur du record ni du codeEquipe sur la branche update. La Public DB étant world-readable, un tiers peut lire les UUID et dateModification réels de n'importe quelle équipe, puis (Authenticated=create, ouvert même après le durcissement « write créateur-seul ») créer SES PROPRES records portant ces mêmes champs avec une dateModification future : ils gagnent le LWW sur tous les appareils de l'équipe, et la date future adoptée localement fait ensuite rejeter toute édition légitime (poison permanent). E2/E3/E4 étendent massivement cette surface (contenu de préparation, scouting, box scores, points, disponibilité/consentement) qui était limitée avant le chantier.
- **Scénario** : Un rival possède un iCloud + l'app et connaît le code équipe (présent en clair dans le lien/QR d'invitation https://playco.app/join/{codeEquipe}/{codeInvitation}, projeté en gymnase). Même mécanique pour falsifier un box score (StatsMatchPartage), marquer un joueur « suspendu », ou passer consentementParentalAtteste à true (falsification d'un registre à valeur légale) via un JoueurPartage spoofé.
- **Vérification (preuves)** : Trouvaille CONFIRMÉE par lecture du code. (1) Aucune occurrence de creatorUserRecordID/lastModifiedUserRecordID dans Playco/Services ni Playco/Models — l'identité du créateur du record n'est jamais vérifiée. (2) fetchRecords (CloudKitSharingService+Import.swift:416-430) sélectionne par simple prédicat sur le CHAMP codeEquipe, sans contrainte de recordName ni de créateur : un record forgé par un tiers authentifié portant ce champ est importé comme un légitime. (3) importerExercice (Preparation.swift:129-139), importerStrategie (:203-213), importerScouting (:287-297), importerBibliotheque (:378-389), importerStatsMatch (Analyse.swift:64-75) et importerJoueur (Import.swift:294-313 + appliquerDisponibilite :338-352, qui écrit consentementParentalAtteste et statutDisponibiliteRaw) rattachent l'entité locale par le CHAMP *ID du record et appliquent un LWW strict par dateModification, sans revérifier codeEquipe sur la branche update ; chaineSecurisee sanitise le contenu, pas la provenance. (4) Le poison par date future est effectif : l'import adopte remoteDateMod (ex. 2030) localement, les éditions légitimes reposent dateModification = Date() (2026 — ExerciceDetailView.swift:127, StrategieDetailView.swift:62-120, JoueurDetailView.swift:234) et sont re-écrasées à CHAQUE cycle de sync tant que le record spoofé existe, car le sweep du coach republie son propre record mais celui de l'attaquant (distinct, date 2030) regagne le LWW à l'import suivant. (5) La Public DB CloudKit autorise par défaut la CRÉATION par tout utilisateur authentifié ; le durcissement « write créateur-seul » (action Dashboard non faite, cf. CLAUDE.md piège #26) ne bloquerait pas la création de nouveaux records ; le codeEquipe est exposé dans le lien/QR d'invitation (LienInvitation.swift). Scénario minimal : compte iCloud tiers + codeEquipe du QR → record ScoutingPartage/StatsMatchPartage/JoueurPartage forgé avec le *ID réel (lisible en Public DB world-readable) et dateModification future → au prochain syncDepuisPublic tous les appareils de l'équipe adoptent les données falsifiées (scouting, box score, statut « suspendu », attestation de consentement parental) et les corrections légitimes sont ignorées de façon récurrente.
